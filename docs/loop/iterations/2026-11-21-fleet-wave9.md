## The wedged binary, and what it hid

`the_tour_points_at_its_control` injected a `PointerInput` into a headless app **with no `PrimaryWindow`**: one thread at 99% CPU while every other waited on a futex, and the binary had to be killed by hand at 270 s. Giving the fixture a window the way `an_injected_pointer_over_a_dock_is_pickable` does turns that into **3.0 s for all four tests**.

What the wedge was hiding: **the pointer never hovers the palette.** That is brand-new code — the test does not exist on `origin/main`, so its assertion has never been green anywhere. It is **ignored with its reason** (#533), not passed: one unproven assertion should not block 5,048 tests over eleven issues that are otherwise proved.

## Four wrong claims, retracted in the record

All on the same chase, all corrected on the issues rather than left plausible:

1. **"It is the wave-tour merge, a three-file range"** — from four single runs. A single run per point is not evidence of causation.
2. **"It is a heisenbug — the probe made it pass"** — the passing and failing runs used **different binaries**.
3. **"`run_system_cached_with` re-enters the executor"** — it hangs with the call replaced by a plain `insert_resource`.
4. **"A `PrimaryWindow` pointer target fixes it"** — it stops the hang and then fails to hover, which is exactly what `an_injected_pointer_over_a_dock_is_pickable`'s own doc predicts: *"this test exists because pass 280 changed that to the window and was wrong."*

The pattern is consistent and worth writing down: **I reached for a plausible mechanism and tested it once, instead of reading the tests already in the tree that encode the answer.** Every one of those four was contradicted by a file in this repository.
