## The CI failure, measured rather than assumed

The owner asked why CI fails. Two different causes, and I was wrong twice before measuring:

**bevy_dark_factory scheduled CI.** Runs since 2026-11-17 die with the test step's conclusion `null` at **16-17 minutes**, reproducibly. The limits the workflow documents (`CARGO_BUILD_JOBS: 3`, `NEXTEST_TEST_THREADS: 2`) have been in place since **2026-11-15**, and the run on **11-16 passed in 95 seconds**.

What I proved:
- The **same command on the same tree passes all 4,953 tests in 822 s** (13.7 min) with 20 GB free — so it is not the code and not the tree.
- There is **no oomd record and no kernel OOM kill** for that window — so "OOM" was my assumption, not a measurement.
- The **prune timer had not run since 11-15**, and CI's cache was **377 GB** on a disk at 96% (176 GB free). One cache exceeded the 40 GiB policy and was pruned, reclaiming 16 GB.

The honest state: the job's 13.7-minute suite sits inside a 16.6-minute wall, so the margin is thin and disk pressure is a real contributor. A fresh run is in flight to test it.

**bevy_gooey CI** is a separate, unfixed failure: "Build examples" links 37 examples (~700 MB) and `ld` is SIGKILLed. The fix is `cargo check --examples --all-features`, which type-checks without linking.

## Ollama Cloud key

Rotated on all four hosts. The dead key was **bmb's** (`904c250e` → `401 Unauthorized`); **big and big_mac had no `OLLAMA_API_KEY` at all**, so ollama-cloud models were failing outright on three of four hosts. Running agents need no restart: no omp process holds the key in its environment, so omp reads `.env` per call.

Also found: the Anthropic account is rate-limited (`retry-after` ~23 h) on `slow` (opus-5-5) and `smol` (haiku); `default` (sonnet) works, so workers are unaffected.
