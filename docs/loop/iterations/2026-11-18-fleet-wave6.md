## The three release failures, in the order they hid each other

The release was attempted four times. Each failure was invisible until the previous one was fixed, and
all three were rebrand leftovers — the rename from Cauldron landed but three files disagreed with it:

1. **The tag prefix.** The workflow triggers on `bevy_dark_factory-v*`; 0.7.0's tag was
   `bevy_cauldron-v0.7.0`. Nothing ran at all — no workflow, no error, just silence. That is the whole
   answer to "why aren't the releases showing".
2. **`Cauldron.icns`.** Every reference in `tools/release/macos/` said `DarkFactory.icns`; the file was
   still `Cauldron.icns`. The app compiled in 40 s and died on `cp: ... No such file or directory`.
3. **`CFBundleExecutable`.** `Info.plist.in` still declared `bevy_cauldron` while `build_app.sh` copies
   the binary as `bevy_dark_factory`. Notarization refused it with *"The executable does not have the
   hardened runtime enabled"* — a message about a **missing** executable, not about the runtime flags,
   which were on both `codesign` calls.

A fourth run then failed its smoke test on focus, which is a runner-screen problem; `publish=true` and
`smoke=false` via `workflow_dispatch` published it.

**Lesson worth keeping:** a rename is not done when the code compiles. Three files named a thing that no
longer existed, and each was only reachable by fixing the one before it.

## Where the hours went

### The stale `.rlib` (six gates)

Six gates died at *compile* with `error[E0433]: cannot find 'issue' in 'feedback'` for a module plainly
present at the top level of the source — plus an `E0277` about `str` that cascaded from it and read like
a genuine type error. The cause: a `blueprint_model` artifact **newer than its source** (`10:07` source,
`11:31` rlib), so cargo's mtime check never rebuilt it. Deleting the artifact fixed it. Recorded in
`docs/loop/RUNNING-A-LOOP.md`.

### The shared lock (three workers, 5-15 minutes each)

`/tmp/fleet/big-heavy.lock` is exclusive by design. I put a bisect on it while three workers' test runs
queued behind it at **0% CPU** — which reads exactly like a hung test and is not one. The runbook now
says: take the lock for a whole-suite run or a cold build, run a single module without it.

### `mac_air` cannot run editor tests

`cargo nextest run -p bevy_dark_factory` sits at 0% CPU for 15+ minutes on an idle host with 58 GB free.
Three workers lost 15-20 minutes each to it. The runbook now says `mac_air` takes no editor tests at all.

### bmb was 100% full

302 MB free, which is why one worker's 329-line test sat uncommitted for hours. Deleting the idle
138 GB `~/.cargo-target-shared/global` (with the owner's approval) took it to 125 GB.

### Gates before checks

The most expensive mistake: running the 45-minute gate **before** `cargo check -p bevy_dark_factory
--tests`, which takes 48 s and would have caught every one of those compile failures.

## Where the workers were right and I was wrong

- **`narrowing_label`.** I told two workers to reuse it from `fleet/airthree`. It reintroduces the
  regression it was meant to fix: writing `min_width: 0` on a row drops the row's automatic minimum to
  nothing, so a block stops reserving its line and the panel's hint text rises under it. Measured:
  `Control(Hint) covers 24x14 px of ink`. The correct fix is the **line break alone**
  (`LineBreak::WordOrCharacter` makes the min-content width the longest word).
- **`#494`'s re-pin.** I asserted `!is_maximised()` after one click from maximised. Wrong — click 2 from
  a raised quarter *does* maximise. The worker measured the four-click sequence and reverted my claim.
- **`#497`'s provenance.** I filed it as pre-existing on the evidence "0 width writes, 28 height writes".
  A probe on `origin/main` showed the pane at **1280 px**, not 1569 — so it was mine. A height change can
  widen a pane, because a UI node in a column takes its children's width. Corrected on the issue, and
  fixed by stating `width: Val(Percent(100.0))`.

## What the next wave should do first

1. Run `cargo check --tests` and `cargo clippy --all-targets -D warnings` **before** launching a gate.
   Every gate failure this wave would have been caught in under a minute.
2. One gate at a time. Two gates against one push worktree collide, and the loser pushes a stale tree.
3. A worker's `PARTIAL` is worth taking: the measured before-numbers are the issue's evidence, and a
   `#[ignore]`d test carrying them is a legitimate deliverable. A fix that was not measured is not.
