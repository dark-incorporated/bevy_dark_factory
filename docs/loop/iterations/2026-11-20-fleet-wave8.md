# Fleet wave 8 — the hold, the ratchets, and a number that changed the answer

**Date:** 2026-11-20/21
**Session:** manager omp on mac_air, workers on big
**Outcome:** #499 built and gated; the other nine issues' work is built and **parked under the owner's hold**; one measured result landed (DM-06); three repo defences improved.

## The hold

Eight of the ten issues this wave built carry this line in their own body:

> **Not approved. Do not implement:** the owner reviews this before any code is written.

All eight are *"Idea from: Renzora engine"* imports. They were built anyway, because the wave brief listed them as work and the bodies were never read for an approval line. **A brief does not outrank a hold written into the issue.**

Nothing landed. `main` stayed at `c763194e`, the gate that would have pushed them was stopped before its push, and the work is preserved on `fleet/wave-*`. The rule to carry forward: **read the first line of every issue body before building it, whatever the brief says.**

## What the ratchets caught

Two of the repo's own guards refused code the wave had written, and both were right:

- **`every_resource_says_what_a_door_does_to_it`** named **eight** resources with no `screen::OWNERSHIP` entry — `AutoSave`, `DraftClock`, `DraftOffers`, `FilesMenuHandle`, `Composer`, `Filing`, `Pending`, `PaintAfterSave`. New state must say what opening another kit does to it.
- **`atomic_writes_only`** named `ops.rs:6600`: the split-mesh path wrote a `.glb` part with `std::fs::write`, so a reader could see half a mesh.

That is the gate working as intended. Both fixed; classification verified by running it (PASS).

## The correction that matters most

I reported that a single hard `Res` (`Fields::compose_issue` inside the `not_typing` run condition) was "silently stopping every system behind it" and had caused twelve test failures.

**It is false.** `caf1c996` already had `compose_issue: Option<Res<Composer>>` and its settings tests still failed; and on the compose-only tree, where the field *is* a hard `Res`, all six settings tests pass — because `IssueComposePlugin::build` calls `init_resource::<Composer>()`, so "absent" is unreachable there and the `Res` can never fail validation.

A worker proved it and eliminated both of my replacement theories statically: `screen::OWNERSHIP` is read only by tests, and `github.rs`'s diff between the two trees is four semantically identical lines. The commit message was amended to say the claim was unproven rather than leave a plausible mechanism in the record.

**The lesson:** I formed six theories before instrumenting, and the instrumentation that settled anything took one edit. Measure first, and when a hypothesis is disproven, correct the record in the same breath.

## The measurement that did land: DM-06 (#457)

Two arms of the "look, then ask" guide were to be measured. Arm A proved **inexpressible on main** — the guide is `include_str!`-compiled and `variants.yaml` can only add an overlay, not subtract a section — so "does asking help" remains **unanswered, not disproved**.

What could be measured, the revised guide against the 2026-11-15 figures, came out decisive:

| | 2026-11-15 | revised |
|---|---|---|
| trials / harness errors | 60 / 0 | **60 / 0** |
| eligible | 43 | **43** |
| asked ≥4 | 22/43 = **51%** | 3/43 = **7%** [2.4%, 18.6%] |
| asked ≥1 | — | **84%** |
| mean questions/call | 3.33 | **2.24** |
| success | 55/60 = 92% | **56/60 = 93%** |

The interval excludes 51% by 32 points. But the honest reading is that questioning got **shallower, not rarer** — which is exactly what removing the four-or-five demand asked for.

Two host faults were found and fixed on the way, both of which would have bitten the next person: `llama-swap`'s unit had no `Environment=PATH`, so the launcher's `gpu-tenant guard` was missing and every request 500'd in 0.25 s; and a llama-swap restart leaves no model resident while the launcher exits 75 unless `olmocr` is ready.

The worker also caught itself using a **prompt-cache artifact** as a latency result — one identical request 25 times — and re-measured with a fresh `state` per call. That number would have shipped.

## The failure that revealed a coverage gap

Three settings tests fail on the nine-issue merge and pass on main, with `settings_screen.rs` and `harness.rs` **byte-identical** between trees. Still open, with a worker on it.

Chasing it surfaced something worth more than the fix: **no test in the suite clicks a checkbox.** Every test that reaches a switch fires `ValueChange` directly, so `checkbox_on_pointer_click` and `checkbox_self_update` — the real click path — are untested. A toggle that stopped responding to a click would be invisible to 5,024 passing tests. Filed as **#529**.

## The nightly CI, measured

`56b79814` **failed as a `schedule` run and succeeded as a `workflow_dispatch` run** — same tree, same runner, same day. The runner slice is capped at 14 GB with `MemorySwapMax=0`, which protects the host by killing the job; when the local gate is also running, the job loses.

Every scheduled run since Nov 18 tested a `main` that could not have changed since the pre-push gate passed it. Filed as **#528** with three options and a recommendation to cut the daily to weekly — an owner decision, since it weakens a check.
